## 二、发现并修复的缺陷：低耗压缩在当前 DSH 版本上从不触发

### 根因

`ToolResultMessage.content[0]` 在当前 DSH 版本为 `ToolResultBlock`，其 `content` 是 **`ContentBlock[]`**（文本在 `content[0].text`）；旧代码：

```js
if (!block || typeof block.content !== 'string') { prev = null; continue }
```

`typeof block.content` 恒为 `'object'`（数组），**每个工具结果都被跳过** —— 实测 `compressAtPercent=0`（强制触发）+ `compressPeakOnly=false` 下 `compressCount` 仍恒为 0。且替换载荷直接写字符串 `content: replacement` 也违反 `ContentBlock[]` 形状，即使通过检查也会破坏消息结构。

### 修复（提交 e617e9c）

- `toolResultText()`：兼容两种形状（字符串 / `ContentBlock[]` 取 `content[0].text`）
- `toolResultContentWith()`：压缩结果以 `ContentBlock[]`（`{type:'text'}`）写回，保持消息形状合法
- 独立脚本验证（真实消息形状 + 真实目录数据）：旧逻辑 0 次压缩；新逻辑 **2305→179 字符（省 92.2%）**，写回形状合法

## 三、低耗压缩多项目实测（修复生效后）

测试手法：每项目产出「大列表 → 同目录加 1 个临时文件再列表」的连续相似长输出（≥1500 字符），压缩在模型读取前改写会话表面。

| 项目 | 原文 | 压缩后 | 节省 |
|------|------|--------|------|
| `dsh-routing-suite-main/preset` | 3550 字符 | ~100 字符 | **~97%** |
| `plugins/`（4 个插件目录） | 2398 字符 | 75 字符 | **96.9%**（省 2323） |
| `dsh-routing-suite-main` 全树 | 3409 字符 | 73 字符 | **97.9%**（省 3336） |

- **端到端生效**：模型收到的工具结果即为压缩版（`[低耗压缩：与上次执行结果仅保留变化]（变化 1 行，原 3409 字符）+ 0.0 KB suite\zzz-temp.txt`）
- **收益保护**：无收益 diff（变化行多、压缩后 ≥40% 原文）被正确拒绝保留原文（日志：`candidate len=2363 → replacement=NO`）
- 调试日志完整决策链示例：

```
seq=129423 curLen=2363 → replacement=NO        （与上一结果差异大，40% 规则拒绝）
seq=129643 curLen=2398 → replacement=75 chars
    REPLACED saved=2323
pass saved=2323 count=1
```

## 四、节省比例分析（与不用插件对比）

### 命中压缩时的直接节省（实测）

**92% ~ 98%** 的工具结果内容。

### 对整体 token 的节省（按工作负载分档估算）

> 公式：总节省 ≈ 工具结果占输入比例 × 可压缩占比 × 压缩率 × 重读效应
> 重读效应：上下文每 token 在长会话中被多次重读（本测试会话实测 213 步 / cacheRead 39.6M / surface 232,923 tok → 平均每 token 重读 **~170 次**，省 1 token 表面 ≈ 省 170 token 账单）

| 负载类型 | 典型场景 | 整体 token 节省 |
|----------|----------|----------------|
| 轻负载 | 少量工具调用、短输出 | 2% ~ 5% |
| 中负载 | 常规 agentic 开发，结果有重复 | 8% ~ 15% |
| 重负载 | 长会话、日志/列表/构建输出密集 | 15% ~ 30% |

### 叠加其他省钱功能

- **错峰半价**：把高峰时段（09-12 / 14-18）工作挪到空闲时段 → 该部分**再省 50%**（面板时段提示 + 倒计时）
- **限额 + 断点截断**：超限后彻底停止 → 避免的支出**无上限**（超限部分 100% 节省）
- **分析采纳**：把小时限额从当前 15.28M 降到官网建议值（高峰 5.09M）→ 更早触发告警/拦截

### 账单视角（重要）

本账户**缓存命中率 98.4%**，输入 token 有效均价极低（¥45.33 / 733.5M ≈ ¥0.062/百万）。压缩的账单价值主要体现在：

1. **削减 cacheRead 总量**（本月 721.98M token 是最大计费项，上下文瘦身直接按比例削减）
2. **未命中输入首写即省**（单价高约 30 倍）
3. **防 context 膨胀** → 减少 compaction / 截断风险

## 五、已知注意点与建议

1. **`lastSession` 为全局变量**：压缩目标会话由最近一次 `assistant/message` 事件决定；多会话并发（如 session-title 的 LLM 调用）时可能作用于其他会话。单用户场景无碍，多会话建议按 sessionId 分别跟踪。
2. **热重载机制**：`LoadCache.delete(url)` + 重导入可强制重新求值；bundle 托管插件热重载若遇「duplicate exact route」需先清路由表再重载（`dev_clear_routes`）。
3. **建议配置**：小时限额设为官网日均÷24（当前 15.28M → 建议高峰生效 5.09M）；低耗压缩建议与断点截断搭配使用（压缩先省输入、超限再硬停）。
